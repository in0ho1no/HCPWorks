# 設計判断の記録

HCPWorks の実装方針のうち、コードを読むだけでは意図が分からないものを記録する。
「なぜそうしたか」「なぜ直さないか」を残すことが目的なので、変更履歴は CHANGELOG.md を参照すること。

## 2026-08-14 保存パスの組み立てを純関数に切り出す

### 背景

画像保存時のパス生成が `filePath.split('.')[0]` だったため、パス全体の最初のドット以降が
切り落とされていた。`my.project/foo.hcp` が `my_<モジュール名>.png` として親ディレクトリへ
保存され、`foo.v1.hcp` と `foo.v2.hcp` が同じ出力ファイルを奪い合う状態だった。
切り詰め先の親ディレクトリは実在することが多く、書き込みが成功してしまうため気付きにくい。

### 判断

`src/utils/save_path.ts` に純関数 `buildSavePathBase()` として切り出し、
`path.dirname` / `path.basename` / `path.extname` でディレクトリ部とファイル名部を分けて扱う。

### 理由

- `FileManager` は fs 操作を担うクラスであり、副作用のないパス組み立てを混ぜると
  テストのためにファイルシステムを用意する必要が生じる。分離すれば文字列比較だけで検証できる
- 同じ組み立てを SVG / PNG / WebP / JPEG の4形式が共有するため、1箇所に集約する価値がある
- テストは `path.join` と `path.sep` でパスを組み立て、Windows・POSIX どちらでも通るようにしている

## 2026-08-14 `#` は行末コメントとして扱い、エスケープ手段を用意する

### 背景

`text.split("#")[0]` により、行頭コメントだけでなく行の途中の `#` 以降も破棄されていた。
`\mod C#で実装する` は `\mod C` になる。エディタ上は全文が見えているのにチャートからは
消えるため、利用者からは原因が分かりにくい。

### 判断

行末コメントは**意図した仕様**として維持する。そのうえで `\#` を「リテラルの `#`」を表す
エスケープとして追加する。

### 理由

- 行末コメントは記述量を抑えられる実用的な機能であり、廃止すると既存の `.hcp` 資産が壊れる
- 一方でエスケープが無いと `C#` のような `#` を含む文言が一切書けず、回避手段もない
- エスケープ記号に `\` を選んだのは、HCP がすでに `\module` `\mod` のように `\` を
  記法プレフィックスとして使っており、利用者にとって追加の学習コストが小さいため

### 適用範囲と注意点

- コメント除去は `cleanTextLines()` `extractModuleMeta()` `extractTables()` の計3箇所にある。
  共通の `removeComment()` へ集約し、処理部・データ部・メタ情報・テーブルセルで挙動を揃える
- `parseModules()` はモジュール名の抽出時のみ `removeComment()` を通す。
  モジュールの**内容**は生の行のまま保持すること。ここで除去してしまうと後段でもう一度
  除去が走り、`\#` が「`#` へ戻ってからコメント開始と解釈される」二重解決が起きる
- 実装は1文字ずつの走査とし、コメント除去とアンエスケープを同時に行う。
  「`\#` ならリテラルの `#` を出力して1文字読み飛ばす／エスケープされていない `#` なら打ち切る」
  という単純な規則で済み、除去後に別途アンエスケープを走らせる必要が無い。
  インデント算出（`indexOf` による位置検索）も、除去後の文字列同士を比較するため影響を受けない
- `\` 自体のエスケープ（`\\#`）は用意しない。「コメント `#` の直前にリテラルの `\` を置く」
  という表現はできなくなるが、実用上の必要性が乏しく、記法を複雑にする対価に見合わない
- README の「`#` から始まる行はコメントです」は実態と異なるため、
  「`#` 以降は行末までコメント」および `\#` の説明へ差し替える

## 2026-08-14 記法キーワードの区切りは半角スペース1文字のみとする

### 背景

`LineType.get_line_type()` は `split(" ")`、モジュール判定は `MODULE_PREFIX = '\module '` と、
いずれも区切りを半角スペース1文字に限定している。そのため `\mod<TAB>foo` は記法として
認識されず通常行になり、`\module<TAB>foo` はモジュール一覧に一切現れない。
エラーも警告も出ない。

### 判断

タブ区切りには**対応しない**。現行仕様のまま維持する。

### 理由

- `.hcp` をテキストとしてそのまま Excel へ貼り付ける運用があり、
  タブ文字はセル区切りとして解釈される。記法の区切りにタブを許すと、
  貼り付け時に意図しない位置で列が分割される
- HCP 書式においてタブは「インデント（レベル）」専用の意味を持たせたい。
  区切りとしても使えるようにすると、1文字が文脈によって二つの意味を持つことになる

### 補足

無言で認識されない点は残るため、README に「キーワードの後は半角スペース1文字で区切る」
ことを明記して予防する。

## 2026-08-14 テーブルの CSV 解釈は現行仕様を維持する

### 背景

`parseTableRow()` はカンマ分割後に空セルを除去するため `a,,c` が2セルになり、列がずれる。
またクォートに対応しないため `x,"1,234",z` は4セルに分割される。

### 判断

どちらも**現行のまま維持**する。

### 理由

- 空セルの除去は意図した仕様。連続したカンマを1つの区切りとみなすことで、
  桁揃えのために余分なカンマを打った表を素直に扱える
- クォート対応は、実装すればエスケープ規則・改行を含むセル・引用符自体の表現まで
  一貫して面倒を見る必要が生じる。影響するのは補足表の見た目のみであり、
  対応負荷に対して得られる利点が小さい。カンマを含む文言は全角カンマ等で回避できる

## 2026-08-14 `.hcp` ファイル判定を共通ヘルパーへ統一する

### 背景

判定が4箇所にあり、書き方が2種類に分かれていた。

- `listingModule` コマンド: `fileName.split('.').pop()?.toLowerCase() !== 'hcp'`（大小文字を無視）
- 3つのイベントハンドラ: `languageId === HCP_ID || fileName.endsWith(HCP_SUFFIX)`（大小文字を区別）

前者は末尾要素を取るため結果としては正しく動くが、後者と読み比べたときに
同じ判定なのか判断できない。

### 判断

`isHcpDocument(document)` を用意して5箇所すべてを置き換える
（コマンド1箇所・イベントハンドラ3箇所・起動時チェック1箇所）。
判定式は `languageId === HCP_ID || fileName.toLowerCase().endsWith(HCP_SUFFIX)` とする。

置き場所は `src/utils/hcp_document.ts` とし、`HCP_ID` と `HCP_SUFFIX` も
`extension.ts` からこのモジュールへ移す。`TIMEOUT` は HCP ファイル判定と無関係なので
`extension.ts` に残す。

### 理由

- 判定ロジックが1箇所に集まり、対象拡張子を増やす際の変更漏れが起きない
- 定数を一緒に移したのは循環参照を避けるため。`extension.ts` に定数を残したまま
  `utils/hcp_document.ts` から参照すると
  `extension → hcp_controller → utils/hcp_document → extension` の循環ができる。
  定数はいずれも `hcp_controller.ts` からしか使われていないため、移動による影響もない
- 大小文字を無視する側に揃えたのは、Windows・macOS の既定のファイルシステムが
  大小文字を区別せず、`FOO.HCP` を別物として扱う理由が無いため。
  イベントハンドラ側は判定がわずかに広がるが、`languageId` による判定が先に効くため
  実質的な挙動変化はほとんどない

## 2026-08-14 設定変更の監視対象と再描画回数

### 背景

`onDidChangeConfiguration` の監視対象が `SvgBgColor` と `WireColorTable` のみで、
`hcpworks.headerDisplay.*`（showName / showScope / showKind）が漏れていた。
これらは `ConfigManager` が読み出してレンダラへ渡しているため、
設定を変更してもファイル保存か Refresh を行うまでプレビューへ反映されない。

また `SvgBgColor` 変更時だけ `updatePreviewByTree()` が即時とフラグ経由の2回呼ばれ、
パースから SVG 生成までが丸ごと二重に実行されていた。

### 判断

`affectsConfiguration('hcpworks.headerDisplay')` を監視対象へ追加する。
再描画はフラグ判定による1回のみとし、即時呼び出しは削除する。

### 理由

- 描画結果に影響する設定はすべて監視対象に含める、という一貫した基準にする。
  個別のキー名ではなく `hcpworks.headerDisplay` を指定することで、
  表示項目が増えても監視側の変更が不要になる
- 再描画は冪等なので二重実行でも表示は壊れないが、
  「フラグを立ててから最後に1回実行する」という元の構造の意図に反しており、
  読み手に例外的な処理があると誤解させる

## 2026-08-14 プレビューの操作系はタイトルバーへ置く

### 背景

プレビューの表示状態（ズーム倍率・ペイン高さ）を永続化したいが、
永続化すると「拡大しすぎて位置を見失う」状態から抜け出せなくなる。
現状は保存のたびに倍率が 1 へ戻るため、これが事実上の復帰手段になっている。
永続化の前に、明示的なリセット手段を用意する必要がある。

### 判断

リセット操作は Webview 内のツールバーではなく、**エディタのタイトルバー**へ
コマンド（`hcpworks.resetPreviewView`）として追加する。
リセットはズーム倍率だけでなくスクロール位置も原点へ戻す。

### 理由

- 保存（`hcpworks.savePreview`）と更新（`hcpworks.refreshPreview`）が
  すでに `editor/title` にボタンとして出ており、操作系がそこに集まる
- VS Code 標準の UI なのでテーマ追従を自前で持つ必要がなく、
  スクロールやスプリッタのドラッグと干渉しない
- アイコンは codicon（`$(screen-normal)`）を用いる。
  light/dark 2枚の SVG を新たに用意する手間が無く、テーマ切り替えにも自動で追従する
- スクロール位置も戻すのは、倍率だけ戻しても画面外を見たままでは
  「全体表示に戻った」ことにならないため

### 補足

- チャート上のダブルクリックによる既存のリセットは倍率のみで、スクロール位置は動かさない。
  挙動を変えると既存利用者の操作感が変わるため、今回は揃えていない
- Webview 内ツールバー案は、倍率の数値表示や拡大・縮小ボタンを置けて発見しやすい反面、
  テーマ追従・レイアウト干渉・ボタンのテストを自前で抱えることになるため見送った。
  なおツールバーを置いても画像には写り込まない（エクスポートは `#svgContainer svg` を
  直列化する方式で、DOM のスクリーンショットではない）

## 2026-08-14 vscode API のスタブはディスクリプタごと差し替える

### 背景

`hcp_controller.test.ts` は `vscode.window.activeTextEditor` などを単純代入で
差し替えていた。`npm run test:unit`（mocha + `src/test/__mocks__/vscode.js`）では通るが、
CI が実行する `npm test`（vscode-test / 実 VSCode 上）では

```
TypeError: Cannot set property activeTextEditor of #<Object> which has only a getter
```

で `setup()` ごと失敗する。実 VSCode の `window` 名前空間では `activeTextEditor` が
**getter のみのアクセサ**として定義されており、コンパイル後のテストは `"use strict"` のため
setter の無いプロパティへの代入が例外になる。
モック側は同じ名前を**データプロパティ**として持つので、この差異がユニットテストでは表面化しない。

### 判断

`stubProperty()` を用意し、`Object.getOwnPropertyDescriptor()` で元のディスクリプタを保存 →
`Object.defineProperty()` で差し替え → 後始末で元のディスクリプタへ復元する方式に統一する。

### 理由

- アクセサ／データプロパティのどちらでも同じ手順で差し替えられ、モックと実 VSCode の差異を
  テストコード側が意識しなくて済む
- 復元もディスクリプタ単位で行うため、getter を「値」で上書きしたまま元に戻せなくなる事故が起きない
- `window.createWebviewPanel` などのメソッドは実 VSCode でも代入可能だが、
  同一ファイル内で方式が混在すると「なぜここだけ違うのか」を毎回確認することになるため揃える

### 注意点

- 実 VSCode では拡張機能自体が activate 済みのため、テストから `initialize()` を呼ぶと
  `registerWebviewViewProvider` が `View provider for '...' already registered` で例外になる。
  `createTreeView` / `registerWebviewViewProvider` もスタブへ差し替えること
  （`createTreeView` は重複登録でも例外を投げないが、方式を揃える意味で同様に扱う）
- `checkOnStartup()` が `executeCommand('hcpworks.listingModule')` を呼ぶため、
  実 VSCode では**実拡張側に登録済みのコマンド**が動いて描画回数が変わりうる。
  `commands.executeCommand` もスタブ化する
- 実 VSCode ではイベント購読が実際に登録されるので、`context.subscriptions` を
  テストごとに `dispose()` すること
- ヘッドレス環境では `npm test` を実行できない（GTK3 が必要）。
  実 VSCode 側でしか起きない差異は、この記録を手掛かりに判断する
