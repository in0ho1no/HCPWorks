# 設計判断の記録

HCPWorks の実装方針のうち、コードを読むだけでは意図が分からないものを記録する。
「なぜそうしたか」「なぜ直さないか」を残すことが目的なので、変更履歴は CHANGELOG.md を参照すること。

## 2026-08-14 保存パスの組み立てを純関数に切り出す

### 背景

画像保存時のパス生成が `filePath.split('.')[0]` だったため、パス全体の最初のドット以降が
切り落とされていた。`my.project/foo.hcp` が `my_<モジュール名>.png` として親ディレクトリへ
保存され、`foo.v1.hcp` と `foo.v2.hcp` が同じ出力ファイルを奪い合う状態だった。
切り詰め先の親ディレクトリは実在することが多く、書き込みが成功してしまうため気付きにくい。

### 判断

`src/utils/save_path.ts` に純関数 `buildSavePathBase()` として切り出し、
`path.dirname` / `path.basename` / `path.extname` でディレクトリ部とファイル名部を分けて扱う。

### 理由

- `FileManager` は fs 操作を担うクラスであり、副作用のないパス組み立てを混ぜると
  テストのためにファイルシステムを用意する必要が生じる。分離すれば文字列比較だけで検証できる
- 同じ組み立てを SVG / PNG / WebP / JPEG の4形式が共有するため、1箇所に集約する価値がある
- テストは `path.join` と `path.sep` でパスを組み立て、Windows・POSIX どちらでも通るようにしている

## 2026-08-14 `#` は行末コメントとして扱い、エスケープ手段を用意する

### 背景

`text.split("#")[0]` により、行頭コメントだけでなく行の途中の `#` 以降も破棄されていた。
`\mod C#で実装する` は `\mod C` になる。エディタ上は全文が見えているのにチャートからは
消えるため、利用者からは原因が分かりにくい。

### 判断

行末コメントは**意図した仕様**として維持する。そのうえで `\#` を「リテラルの `#`」を表す
エスケープとして追加する。

### 理由

- 行末コメントは記述量を抑えられる実用的な機能であり、廃止すると既存の `.hcp` 資産が壊れる
- 一方でエスケープが無いと `C#` のような `#` を含む文言が一切書けず、回避手段もない
- エスケープ記号に `\` を選んだのは、HCP がすでに `\module` `\mod` のように `\` を
  記法プレフィックスとして使っており、利用者にとって追加の学習コストが小さいため

### 適用範囲と注意点

- コメント除去は `cleanTextLines()` `extractModuleMeta()` `extractTables()` の計3箇所にある。
  共通の `removeComment()` へ集約し、処理部・データ部・メタ情報・テーブルセルで挙動を揃える
- `parseModules()` はモジュール名の抽出時のみ `removeComment()` を通す。
  モジュールの**内容**は生の行のまま保持すること。ここで除去してしまうと後段でもう一度
  除去が走り、`\#` が「`#` へ戻ってからコメント開始と解釈される」二重解決が起きる
- 実装は1文字ずつの走査とし、コメント除去とアンエスケープを同時に行う。
  「`\#` ならリテラルの `#` を出力して1文字読み飛ばす／エスケープされていない `#` なら打ち切る」
  という単純な規則で済み、除去後に別途アンエスケープを走らせる必要が無い。
  インデント算出（`indexOf` による位置検索）も、除去後の文字列同士を比較するため影響を受けない
- `\` 自体のエスケープ（`\\#`）は用意しない。「コメント `#` の直前にリテラルの `\` を置く」
  という表現はできなくなるが、実用上の必要性が乏しく、記法を複雑にする対価に見合わない
- README の「`#` から始まる行はコメントです」は実態と異なるため、
  「`#` 以降は行末までコメント」および `\#` の説明へ差し替える

## 2026-08-14 記法キーワードの区切りは半角スペース1文字のみとする

### 背景

`LineType.get_line_type()` は `split(" ")`、モジュール判定は `MODULE_PREFIX = '\module '` と、
いずれも区切りを半角スペース1文字に限定している。そのため `\mod<TAB>foo` は記法として
認識されず通常行になり、`\module<TAB>foo` はモジュール一覧に一切現れない。
エラーも警告も出ない。

### 判断

タブ区切りには**対応しない**。現行仕様のまま維持する。

### 理由

- `.hcp` をテキストとしてそのまま Excel へ貼り付ける運用があり、
  タブ文字はセル区切りとして解釈される。記法の区切りにタブを許すと、
  貼り付け時に意図しない位置で列が分割される
- HCP 書式においてタブは「インデント（レベル）」専用の意味を持たせたい。
  区切りとしても使えるようにすると、1文字が文脈によって二つの意味を持つことになる

### 補足

無言で認識されない点は残るため、README に「キーワードの後は半角スペース1文字で区切る」
ことを明記して予防する。

## 2026-08-14 テーブルの CSV 解釈は現行仕様を維持する

### 背景

`parseTableRow()` はカンマ分割後に空セルを除去するため `a,,c` が2セルになり、列がずれる。
またクォートに対応しないため `x,"1,234",z` は4セルに分割される。

### 判断

どちらも**現行のまま維持**する。

### 理由

- 空セルの除去は意図した仕様。連続したカンマを1つの区切りとみなすことで、
  桁揃えのために余分なカンマを打った表を素直に扱える
- クォート対応は、実装すればエスケープ規則・改行を含むセル・引用符自体の表現まで
  一貫して面倒を見る必要が生じる。影響するのは補足表の見た目のみであり、
  対応負荷に対して得られる利点が小さい。カンマを含む文言は全角カンマ等で回避できる

## 2026-08-14 `.hcp` ファイル判定を共通ヘルパーへ統一する

### 背景

判定が4箇所にあり、書き方が2種類に分かれていた。

- `listingModule` コマンド: `fileName.split('.').pop()?.toLowerCase() !== 'hcp'`（大小文字を無視）
- 3つのイベントハンドラ: `languageId === HCP_ID || fileName.endsWith(HCP_SUFFIX)`（大小文字を区別）

前者は末尾要素を取るため結果としては正しく動くが、後者と読み比べたときに
同じ判定なのか判断できない。

### 判断

`isHcpDocument(document)` を用意して5箇所すべてを置き換える
（コマンド1箇所・イベントハンドラ3箇所・起動時チェック1箇所）。
判定式は `languageId === HCP_ID || fileName.toLowerCase().endsWith(HCP_SUFFIX)` とする。

置き場所は `src/utils/hcp_document.ts` とし、`HCP_ID` と `HCP_SUFFIX` も
`extension.ts` からこのモジュールへ移す。`TIMEOUT` は HCP ファイル判定と無関係なので
`extension.ts` に残す。

### 理由

- 判定ロジックが1箇所に集まり、対象拡張子を増やす際の変更漏れが起きない
- 定数を一緒に移したのは循環参照を避けるため。`extension.ts` に定数を残したまま
  `utils/hcp_document.ts` から参照すると
  `extension → hcp_controller → utils/hcp_document → extension` の循環ができる。
  定数はいずれも `hcp_controller.ts` からしか使われていないため、移動による影響もない
- 大小文字を無視する側に揃えたのは、Windows・macOS の既定のファイルシステムが
  大小文字を区別せず、`FOO.HCP` を別物として扱う理由が無いため。
  イベントハンドラ側は判定がわずかに広がるが、`languageId` による判定が先に効くため
  実質的な挙動変化はほとんどない

## 2026-08-14 設定変更の監視対象と再描画回数

### 背景

`onDidChangeConfiguration` の監視対象が `SvgBgColor` と `WireColorTable` のみで、
`hcpworks.headerDisplay.*`（showName / showScope / showKind）が漏れていた。
これらは `ConfigManager` が読み出してレンダラへ渡しているため、
設定を変更してもファイル保存か Refresh を行うまでプレビューへ反映されない。

また `SvgBgColor` 変更時だけ `updatePreviewByTree()` が即時とフラグ経由の2回呼ばれ、
パースから SVG 生成までが丸ごと二重に実行されていた。

### 判断

`affectsConfiguration('hcpworks.headerDisplay')` を監視対象へ追加する。
再描画はフラグ判定による1回のみとし、即時呼び出しは削除する。

### 理由

- 描画結果に影響する設定はすべて監視対象に含める、という一貫した基準にする。
  個別のキー名ではなく `hcpworks.headerDisplay` を指定することで、
  表示項目が増えても監視側の変更が不要になる
- 再描画は冪等なので二重実行でも表示は壊れないが、
  「フラグを立ててから最後に1回実行する」という元の構造の意図に反しており、
  読み手に例外的な処理があると誤解させる

## 2026-08-14 ラスタライズ画像の長辺に上限を設ける

### 背景

画像エクスポートは倍率2倍固定でラスタライズしていた。Canvas には寸法の上限があり、
超えた場合は**例外を投げないまま空の画像が出力される**。
実測では処理150行程度のモジュールで既に上限へ達しており、机上の懸念ではない。

| 処理行数 | SVG寸法 | 2倍時 |
| --- | --- | --- |
| 100行 | 161x3110 | 322x6220（上限内） |
| 150行 | 168x4610 | 299x9220（上限超過） |
| 300行 | 168x9110 | 336x18220（大幅超過） |

### 判断

長辺の上限を 8192 ピクセルとし、2倍しても収まる場合のみ2倍を維持する。
超える場合は長辺が上限に一致する倍率まで下げ、等倍でも超える場合は縮小する。

### 理由

- 上限値はブラウザや GPU に依存して確定値が無いため、広く安全とされる 8192 を採る。
  PlantUML の VSCode 拡張がクリップボードコピーで採用している値でもある
- 面積ではなく長辺で判定するのは、長辺が 8192 に収まれば面積も 8192^2 に収まり、
  Chromium の面積上限にも同時に収まるため。判定を1つに保てる
- 切り取り（クロップ）ではなく縮小を選んだのは、図の一部が欠けるより
  解像度が落ちる方が実害が小さいため

### 補足

- あわせて `canvas.width` へ渡す値を `Math.round()` し、`drawImage()` にも同じ値を使うようにした。
  `canvas.width` は整数へ切り捨てられるため、倍率が小数になると描画サイズと1ピクセルずれる
- 上限は `SvgContent.MAX_EXPORT_PIXELS` として公開し、Webview のテンプレートへ埋め込む。
  倍率計算そのものは Webview 内のインラインスクリプトにあるため、
  実行時の検証には SVG の寸法プロパティと Canvas のスタブが要る
  （後述の「Webview の挙動は jsdom 上で検証する」を参照）

## 2026-08-14 プレビューの操作系はタイトルバーへ置く

> **この判断は 2026-08-16「プレビューの表示操作は Webview 内ツールバーへ移す」で置き換えた。**
> クリップボードへのコピーがタイトルバーからでは実現できず、前提が変わったため。

### 背景

プレビューの表示状態（ズーム倍率・ペイン高さ）を永続化したいが、
永続化すると「拡大しすぎて位置を見失う」状態から抜け出せなくなる。
現状は保存のたびに倍率が 1 へ戻るため、これが事実上の復帰手段になっている。
永続化の前に、明示的なリセット手段を用意する必要がある。

### 判断

リセット操作は Webview 内のツールバーではなく、**エディタのタイトルバー**へ
コマンド（`hcpworks.resetPreviewView`）として追加する。
リセットはズーム倍率だけでなくスクロール位置も原点へ戻す。

### 理由

- 保存（`hcpworks.savePreview`）と更新（`hcpworks.refreshPreview`）が
  すでに `editor/title` にボタンとして出ており、操作系がそこに集まる
- VS Code 標準の UI なのでテーマ追従を自前で持つ必要がなく、
  スクロールやスプリッタのドラッグと干渉しない
- アイコンは codicon（`$(screen-normal)`）を用いる。
  light/dark 2枚の SVG を新たに用意する手間が無く、テーマ切り替えにも自動で追従する
- スクロール位置も戻すのは、倍率だけ戻しても画面外を見たままでは
  「全体表示に戻った」ことにならないため

### 補足

- チャート上のダブルクリックによる既存のリセットは倍率のみで、スクロール位置は動かさない。
  挙動を変えると既存利用者の操作感が変わるため、今回は揃えていない
- Webview 内ツールバー案は、倍率の数値表示や拡大・縮小ボタンを置けて発見しやすい反面、
  テーマ追従・レイアウト干渉・ボタンのテストを自前で抱えることになるため見送った。
  なおツールバーを置いても画像には写り込まない（エクスポートは `#svgContainer svg` を
  直列化する方式で、DOM のスクリーンショットではない）

## 2026-08-14 vscode API のスタブはディスクリプタごと差し替える

### 背景

`hcp_controller.test.ts` は `vscode.window.activeTextEditor` などを単純代入で
差し替えていた。`npm run test:unit`（mocha + `src/test/__mocks__/vscode.js`）では通るが、
CI が実行する `npm test`（vscode-test / 実 VSCode 上）では

```
TypeError: Cannot set property activeTextEditor of #<Object> which has only a getter
```

で `setup()` ごと失敗する。実 VSCode の `window` 名前空間では `activeTextEditor` が
**getter のみのアクセサ**として定義されており、コンパイル後のテストは `"use strict"` のため
setter の無いプロパティへの代入が例外になる。
モック側は同じ名前を**データプロパティ**として持つので、この差異がユニットテストでは表面化しない。

### 判断

`stubProperty()` を用意し、`Object.getOwnPropertyDescriptor()` で元のディスクリプタを保存 →
`Object.defineProperty()` で差し替え → 後始末で元のディスクリプタへ復元する方式に統一する。

### 理由

- アクセサ／データプロパティのどちらでも同じ手順で差し替えられ、モックと実 VSCode の差異を
  テストコード側が意識しなくて済む
- 復元もディスクリプタ単位で行うため、getter を「値」で上書きしたまま元に戻せなくなる事故が起きない
- `window.createWebviewPanel` などのメソッドは実 VSCode でも代入可能だが、
  同一ファイル内で方式が混在すると「なぜここだけ違うのか」を毎回確認することになるため揃える

### 注意点

- 実 VSCode では拡張機能自体が activate 済みのため、テストから `initialize()` を呼ぶと
  `registerWebviewViewProvider` が `View provider for '...' already registered` で例外になる。
  `createTreeView` / `registerWebviewViewProvider` もスタブへ差し替えること
  （`createTreeView` は重複登録でも例外を投げないが、方式を揃える意味で同様に扱う）
- `checkOnStartup()` が `executeCommand('hcpworks.listingModule')` を呼ぶため、
  実 VSCode では**実拡張側に登録済みのコマンド**が動いて描画回数が変わりうる。
  `commands.executeCommand` もスタブ化する
- 実 VSCode ではイベント購読が実際に登録されるので、`context.subscriptions` を
  テストごとに `dispose()` すること
- ヘッドレス環境では `npm test` を実行できない（GTK3 が必要）。
  実 VSCode 側でしか起きない差異は、この記録を手掛かりに判断する

## 2026-08-14 Webview の挙動は jsdom 上で検証する

### 背景

Webview の HTML・CSS・JavaScript は `svg_content.ts` の `getHtmlWrappedSvg()` が
テンプレート文字列として生成する。そのため従来のテストは
「生成された文字列に特定の記述が含まれるか」しか検証できず、
スクロール位置の復元・ズーム・スプリッタ・エクスポートといった**実行時の挙動には
自動テストが一切無かった**。

### 判断

`jsdom` を devDependency に追加し、生成HTMLを実際に実行して検証する。
文字列検査（`svg_content.test.ts`）と実行時検証（`svg_content_runtime.test.ts`）は
ファイルを分ける。

### 理由

- `@vscode/test-electron` では Webview が iframe で隔離されており、中の DOM に手が届かない。
  そのうえ GUI が必要でヘッドレス環境では実行できない
- Playwright なら実レイアウトまで検証できるが、CI でのブラウザ取得を含めて重く、
  得られる範囲に対して割に合わない
- `tsconfig.json` の変更は不要だった。`lib` に `"DOM"` を足すと拡張機能側のコードで
  誤って `document` を使ってもエラーにならなくなるが、jsdom の型は自己完結しているため
  その心配がない

### ハーネスを書くときの注意点

- `runScripts: 'dangerously'` を指定しないとインラインスクリプトが実行されない
- `pretendToBeVisual: true` が必要。スクロール位置の復元が `requestAnimationFrame` を使う
- `beforeParse` で `acquireVsCodeApi` をスタブする。スクリプトの先頭で呼ばれるため、
  パース後では間に合わない
- jsdom は**別の realm** で動くため、`postMessage` や `setState` で受け取った
  オブジェクトはプロトタイプが Node 側と異なる。`deepStrictEqual` は構造が同じでも
  不一致になるので、比較前に `JSON.parse(JSON.stringify(...))` で変換する
- `window.close()` をテストごとに呼ぶ。`pretendToBeVisual` は
  `requestAnimationFrame` のループを回し続ける

### 検証できない範囲

- **見た目**。ツールバーの重なり、テーマごとの視認性、折り返しの崩れは目視でしか確認できない
- **レイアウト計算**。jsdom にレイアウトエンジンが無く `getBoundingClientRect()` は常に 0 を返す。
  スプリッタのテストが「ドラッグ量がそのまま高さになる」形で書けているのはこのため
- **Canvas と SVG の寸法プロパティ**。どちらも jsdom は未実装なので、
  エクスポート処理の検証にはスタブが要る。したがって検証できるのは
  「倍率計算と Canvas への寸法指定が正しいか」までで、実際に描画された画素は確認できない
- **クリップボード**。`navigator.clipboard` も `ClipboardItem` も存在しないため、
  コピー機能についても「正しい引数で API を呼んだか」までしか検証できない
  （後述の「プレビューの表示操作は Webview 内ツールバーへ移す」を参照）

## 2026-08-16 プレビューの表示操作は Webview 内ツールバーへ移す

### 背景

チャートをクリップボードへ画像としてコピーしたい。
ブラウザのクリップボード書き込みは「書き込む文書がフォーカスされていること」と
「ユーザー操作起点であること」を要求する。
タイトルバーのコマンドから起動すると、処理は拡張機能側で走って Webview には
`postMessage` が届くだけになるため、Webview から見るとユーザー操作起点ではなく、
フォーカスも無い可能性がある。この場合 `NotAllowedError` で失敗する。

つまりコピーボタンは**Webview 内にある必要がある**。
これは「操作系はタイトルバーへ置く」という 2026-08-14 の判断と衝突する。

### 判断

プレビュー最上部に固定の1行としてツールバーを設け、
**表示のリセット（Reset View）とクリップボードへのコピー（Copy Image）を両方そこへ置く**。
あわせてタイトルバーからリセットボタン（`editor/title` の
`hcpworks.resetPreviewView`）を外す。コマンド自体は残し、コマンドパレットからは使える。

成否は Webview 内のトーストで伝える（`Copied to clipboard` / `Copy failed` /
`Clipboard is not available`）。

### 理由

- コピーが Webview 内でしか成立しない以上、リセットだけタイトルバーに残すと
  表示操作が2箇所へ分散する。同種の操作は同じ場所にある方が見つけやすい
- タイトルバーのリセットを残すと、リセット手段がタイトルバー・ツールバー・
  ダブルクリックの3つになる。タイトルバーのボタンは未リリース（`[Unreleased]`）のため、
  今外しても既存利用者の操作は変わらない
- 更新（`hcpworks.refreshPreview`）と保存（`hcpworks.savePreview`）はタイトルバーへ残す。
  これらは Webview の表示状態ではなくファイルに対する操作で、性質が違う
- トーストを選んだのは、書き込みが Webview 内で完結するのに通知だけ拡張機能へ
  往復させる理由が無いため。テストも Webview 側だけで閉じる
- ツールバーを浮かせず固定の1行にしたのは、`svgPane` のスクロールや
  スプリッタのドラッグと干渉させないため。消費するのは縦数十ピクセルで済む

### 実装上の注意点

- **ツールバーとトーストは `#svgContainer` の外に置くこと。**
  エクスポートは `document.querySelector('#svgContainer svg')` を直列化する方式なので、
  外にある限り出力画像へ写り込まない。内側に入れると混入する。
  これは jsdom で構造として検証してある
- ツールバーを載せるため `body` を縦方向の flex にし、`.split-container` の
  `height: 100vh` を `flex: 1` + `min-height: 0` へ変えた。
  `min-height: 0` が無いとペインのスクロールが効かなくなる
- 色は `var(--vscode-*)` を使う。テーマ追従を自前で持たないため
- 倍率計算はエクスポートと共有する。Webview 側の `rasterize()` が
  「Canvas を作るところまで」を担い、`toDataURL()` と `toBlob()` の違いは
  呼び出し側が持つ。上限は `SvgContent.MAX_EXPORT_PIXELS`
- リモート開発でも正しく動く。Webview は手元の VS Code UI プロセスで動くため、
  WSL2 環境でも Windows 側のクリップボードへ載る。
  拡張機能ホスト側で OS コマンド（`xclip` 等）を叩く方式にはこの利点が無い

### 検証できない範囲

`navigator.clipboard` も `ClipboardItem` も jsdom には無いため、
テストで確認できるのは「`image/png` の Blob を渡して API を呼んだか」
「失敗時に正しく表示したか」まで。
**実際に画像がクリップボードへ載ったかは実機での目視確認が要る。**
ツールバーの見た目（テーマごとの視認性、折り返し）も目視のみ。

## 2026-08-16 プレビューの表示状態はモジュール単位で永続化する

### 背景

ズーム倍率・スクロール位置・表領域の高さは、プレビューを更新するたびに初期値へ戻っていた
（保持していたのはスクロール位置のみ）。同じモジュールを編集しながら見比べる場面では、
保存のたびに拡大し直す必要がある。

一方、単純に保存するだけでは体験が悪化する。Webview の状態はパネル単位で保持されるが、
パネルはモジュールを切り替えても使い回されるため、別のモジュールへ切り替えたときに
前のモジュールの倍率がそのまま適用されてしまう。

### 判断

次の3点を同時に入れる。どれか1つでも欠けると、永続化しない方がましな状態になる。

1. **キー分け** — 「元ファイルパス + モジュール名」を保存キーとする（`SvgContent.getStateKey()`）
2. **クランプ** — 復元時に倍率をズームの許容範囲へ、表領域の高さを
   `[60px, ウィンドウ高さの85%]` へ収める
3. **デバウンス** — 保存を 200ms 間引く（`SvgContent.SAVE_DEBOUNCE_MS`）

保持件数は直近 20 件（`SvgContent.MAX_STATE_ENTRIES`）とし、超えた分は古い順に捨てる。

### 理由

- キーに元ファイルパスを含めるのは、別ファイルに同じモジュール名がありうるため。
  区切りは改行文字とした。パスにもモジュール名にも現れないため、
  「パスの末尾 + 区切り + 空のモジュール名」が別の組み合わせと衝突しない
- ペイン高さは絶対ピクセルで保存するため、当時より小さいウィンドウで開くと
  画面をほぼ占有してしまう。倍率も同様に、壊れた値や範囲外の値が入ると操作不能になる。
  保存側ではなく**復元側**で収めるのは、保存後にウィンドウの大きさが変わりうるため
- スクロールとズームは1操作で何度もイベントが飛ぶ。間引かないと `setState` の呼び出しが
  操作のたびに数十回になる
- 件数に上限を設けるのは、パネルが生きている限り状態が積み上がるため。
  20 件は「作業中に行き来するモジュール数」として十分で、捨てても影響が小さい範囲

### 実装上の注意点

- **単発の操作は間引かずにその場で保存する。** リセット、ダブルクリック、
  スプリッタのドラッグ完了がこれにあたる。間引くと保存前に画面が差し替わりうる
- **破棄・非表示のタイミングでフラッシュする。** `beforeunload` に加えて `pagehide` と
  `visibilitychange` でも保存する。プレビューの更新は `webview.html` の差し替えで行うため、
  間引き待ちのまま差し替わると保存が失われる
- 復元は「保存済みの配列から自分のキーの記録を探す」形にし、見つからなければ既定値で動く。
  壊れた状態（`entries` が配列でない等）でも例外を投げずに初期状態から始めること
- **キーを `<script>` 内へ埋め込む際は `toScriptLiteral()` を使う。**
  `JSON.stringify()` は `<` をエスケープしないため、そのまま埋め込むとモジュール名に
  `</script><script>...` を含めるだけで任意のコードが動く。`.hcp` の内容は
  利用者が書いたものとは限らないので、信用できない入力として扱う。
  SVG 側は `SvgFigureText.escapeXml()` が同じ役割を担っている
- ペイン高さの上限にウィンドウ高さの85%を使うのは、CSS の `.table-pane { max-height: 85% }`
  と揃えるため。片方だけ変えると、CSS 側で抑えられて保存値と表示が食い違う

### 状態が残る範囲

`vscode.getState()` / `setState()` の状態は **`WebviewPanel` が生きている間だけ**保持され、
パネルを閉じると破棄される。したがって「同じモジュールを開き直すと復元される」のは
**プレビューパネルを開いたままモジュールを切り替えた場合**に限られる。
README にはこの範囲を明記すること。

パネルを閉じても保持したい場合は次が必要になるが、現時点では入れていない。

- 保存先を `context.workspaceState` へ移す（拡張機能ホスト側へ `postMessage` して保存する）
- VS Code の再起動をまたいでパネル自体を復元するなら `WebviewPanelSerializer` を登録する

見送っているのは、現状の用途が「編集しながら見比べる間の倍率保持」であり、
その範囲ならパネルの寿命と一致していて困らないため。
保存先を増やすと、どちらが正かを決める処理と、ワークスペースをまたいだ掃除が必要になる。

### 補足

- ズーム倍率が復元されるようになったことで、「拡大したまま位置を見失う」状態が
  モジュールを切り替えて戻ってきても続くようになった。ツールバーの Reset View が
  その復帰手段になる
  （2026-08-16「プレビューの表示操作は Webview 内ツールバーへ移す」を参照）
- ダブルクリックによるリセットは従来どおり倍率のみで、スクロール位置は動かさない。
  ただし倍率が永続化されたため、リセット結果はその場で保存するようにした
